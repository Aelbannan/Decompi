## CRITICAL

**1. The pipeline/step model cannot express v1's core execution semantics — batching, retry routing, or triggered finalization. (§10, §6.2 `run_workers`)**
`Pipeline.steps` is a flat list; `plan()` returns items; nothing defines whether steps run per-item, per-batch, or per-run. This matters because v1's entire cost structure is *batching*: `batchSize: 5` targets share ONE agent session and one brief (`orchestrator.ts`, `buildBatchBrief`). As specified, decompi runs one agent step per work item — a ~5× session-cost regression on day one. Also inexpressible: size-based retry routing (`singletonMinSize` → singleton sessions at a *harder* model vs rebatch pool at a cheaper one — per the README this asymmetry is deliberate), and the TU-final trigger ("when a unit reaches zero unmatched, run finalization"). The schema bakes in the wrong unit of concurrency too: `run_workers.work_item_id` is singular, one item per worker.
**Fix:** add a `foreach`/`batch` step kind (group items into batches of N with a shared prompt context), allow per-step `onReject` routing to named sub-pipelines with their own model and attempt budget, and add an event trigger construct (`on unitComplete → run pipeline tu-final`). Make M3's acceptance "drives one TU end-to-end *with batched sessions and singleton/rebatch routing*", and make `run_workers` a worker→items join or drop the column.

**2. The "witness is an external native tool, not Python from this repo" claim is factually false, and it silently breaks the flagship "No Python" goal. (§1, §9, §20)**
The register-renaming witness is `tools/coop/lib/renaming_witness.py` on top of `tools/ppc_equivalence` — ~61k lines of Python using **z3 Python bindings**, in this repo. §1 says the witness "remains an external native tool invoked like objdump — not Python scripts from this repo." That misdescribes the status quo. M5's acceptance ("Python path deprecated") plus "No Python scripts" either forces a 61k-line SMT reimplementation in TS (absurd) or contradicts itself by keeping a Python dependency forever.
**Fix:** amend §1: the witness is a *versioned external process dependency* (Python+z3) that decompi shells out to, exactly like MWCC/ninja/objdiff. State explicitly that `tools/ppc_equivalence` + `.venv` provisioning stay in scope and are carved out of the deprecation; drop the word "native." This is also a portability question for §20 — "other games define their own witnessCommand (or none)" is fine, but the Xenoblade adapter's witness story must be written honestly.

**3. The byte-match verifier is a massive hidden reimplementation with no milestone, and it's misplaced in core. (§4 `src/verify/byte-match.ts`, §9, §19)**
"TS hexdiff (build → ELF parse → instruction diff + reloc handling)" replaces `hexdiff.py` (1,714 lines), which itself depends on `tools/ppc_equivalence.elf_symbols/decoder/ir` (ELF parsing, PPC opcode decoding), `reloc_map.py` (911 lines: reloc name-drift analysis + approved `extern "C"` fix suggestions), `object_size.py` (split-budget checks), stripped-DOL retail-name recovery via registry address matching, and regswap/pure-regswap/structural classification. None of this appears in any milestone. Worse, `byte-match.ts` sits in `src/verify/` (core) while being entirely PPC/ELF/DOL/MWCC-specific — a direct violation of Principle 1 ("core has zero knowledge of MWCC, PPC").
**Fix:** delete the built-in byte-match verifier from core; keep only the `Verifier` interface and let `GameAdapter.diff()/verify()` provide it (the interface already exists — use it). Add an explicit milestone between M2 and M3 for the Xenoblade diff engine with a parity harness diffing its JSON output against `hexdiff.py --json` on a golden unit set.

**4. The actual acceptance engine is missing entirely: objdiff unit reports, data/fuzzy percentages, and torn-write backoff. (§9, §3)**
Acceptance in v1 runs through `tools/coop/lib/objdiff_report.py::evaluate_unit_match` — objdiff report parsing with code/data/fuzzy match %, per-function status, and a documented retry backoff (`_REPORT_RETRY_BACKOFF_S`) for the multi-agent race where concurrent ninja runs leave the decomp `.o` mid-write and a byte-identical draft was mis-evaluated NOT_STARTED (runs 3–4, acceptances lost). The spec's verifier list (byte-match/witness/behaviour/fakematch) has no unit-level report verifier, no data-match concept — yet TU-final "verifies the whole TU (including data)." §3's "port lessons" list omits this lesson.
**Fix:** add an adapter-provided `unitReport` verifier (objdiff run + report parse + the documented backoff), record the torn-`.o` race in §3, and require M5 acceptance to reproduce `evaluate_unit_match` verdicts on recorded cases.

## HIGH

**5. §5's build-lock rule reintroduces the run30 incident.**
"The daemon runs the build (and any external native tools) under the same repo-wide advisory lock." `run.py cmd_cycle` does the opposite, with the reason in a comment: the lock is held across build + immediate `.o` reads only, and is *deliberately not held* when the witness/z3 runs — "a z3 simplify under the lock froze every agent for ~30 min (run30 incident)."
**Fix:** §5 must say: lock covers build + post-build `.o` reads; witness/SMT and any long external analysis run *outside* the lock. Port the comment verbatim.

**6. Migration is one line and drops load-bearing state; acceptance semantics depend on fields the schema doesn't have. (§6.2, §8, M5)**
`targets.json` is 19,300 rows × ~30 fields, and acceptance reads them: `cmd_cycle` replays a target's stored `equivalence_certificate`/`declared_return` during re-proofs; `equivalence_status/confidence/policy`, `required_level`, `instruction_match`, `workflow_status` (a second axis: DISCOVERY/BACKLOG/ACTIVE/ACCEPTED/REVALIDATION_REQUIRED), and callgraph fields all drive behavior. `targets.certs.jsonl.gz` (7MB of certificates) and `ledger.jsonl` (attempt counts that drive `maxAttemptsPerTarget` exhaustion) are unmentioned — losing exhaustion state means agents re-burn money on known-dead targets. The `work_items` schema has no `required_level`, no workflow axis, no cert fields.
**Fix:** a migration section with a field-by-field mapping (column vs `meta` JSON), mandatory id preservation (ledger and certs reference target ids), explicit import of exhaustion/attempt state and certificates, and an acceptance check: migrated DB reproduces `run.py targets status` output and the exhausted-set exactly.

**7. Registry-maintenance tooling has no replacement anywhere. (§15, §19)**
The coop tooling isn't just matching: `targets scan-source` (discover new `func_*`), `sync-calls`/`sync-symbols` (callgraph maintenance), `recertify --bottom-up` (cert cascade after edits), `validate`, `dedupe`, `import-symbols`, `audit-promotion`, `reloc-map mine/diff/ensure-fresh`, `size`, `progress`, `ctx`, `triage`. None appear in the CLI or milestones. Deprecating the Python path in M5 leaves agents without the tools that keep the registry truthful.
**Fix:** scope these as adapter-level commands in a milestone (M5 acceptance should include them), or explicitly keep the Python registry tools alive post-M5.

**8. Two status systems, one column. (§8 vs §6.2)**
§8 defines a canonical lifecycle (`pending → claimed → active → verified → accepted | rejected`) "tracked independently of the adapter's status vocab" — but `work_items` has a single `status` column typed as adapter vocab. Xenoblade reality needs both axes (`status` ladder + `workflow_status`).
**Fix:** add a core-owned `lifecycle` column beside adapter-owned `status` (plus `required_level`), or delete the canonical lifecycle from §8.

**9. Selectors can't express the call-graph wave — the authoritative selection mode. (§8)**
v1 selection is call-graph-gated (`isCallGraphReady`, `called_functions` ⊆ matched, `--selection ready`, `callgraph_status`). Selector filters are status/kind/unit/size/meta-equality; "all callees resolved and matched" is a recursive predicate over a JSON array — unexpressible, and not compilable to SQL under §3's rules.
**Fix:** materialize derived columns (`ready`, `attempts`, `exhausted`, `milestone`, `region`) on `work_items`, maintained by the engine on status change; document that selectors filter over materialized columns. This also fixes `greenfieldOnly`-style selection.

**10. Selector-over-`meta` contradicts the portable-SQL principle, and breaks LIMIT semantics. (§3.2 vs §8)**
JSON-as-TEXT with no JSON1/JSONB means `meta` ops (`contains`, `regex`) require full-table scan + app-side filtering — after which `LIMIT` can no longer be pushed down, so "first 50 X where meta.y=…" silently becomes "filter everything, then take 50" (fine at 19k rows, but the spec *claims* "compiled to SQL").
**Fix:** promote hot meta keys to real columns (see #9); restrict `filter.meta` to documented app-side post-filtering; or add an engine-capability flag permitting JSON operators per adapter.

**11. Standalone CLI mode violates the single-writer model. (§5, §6.1)**
"A standalone single-run mode … opens the same store directly" = a second SQLite writer concurrent with the daemon: `database is locked` errors under WAL (one writer, ever), and `events.seq` "app-assigned monotonic" (read MAX, +1) races between processes.
**Fix:** standalone mode uses a scratch DB or refuses while the daemon holds a lockfile; better, all CLI commands are daemon RPCs, period. Make `events.seq` engine-assigned (rowid/BIGSERIAL behind the SqlAdapter) rather than app-assigned.
