# Adversarial Review — Decompi SPEC.md

## CRITICAL

### C1 — `byte-match` verifier is misplaced: it is not game-agnostic, yet it sits in core. (§9, §7, §4)
**Problem.** §9 lists `byte-match` as a *core* built-in verifier ("TS hexdiff — build → ELF parse → instruction diff + reloc handling. Replaces `tools/coop/hexdiff.py`"). But `hexdiff.py` is 1,714 lines of MWCC/PPC/ELF-specific logic plus a 911-line `reloc_map.py` doing MWCC archive-global `@N` reloc canonicalization. Meanwhile §7 puts `buildUnit`/`diff` in the `GameAdapter`. So who owns ELF parsing and reloc handling — core's `byte-match` or the adapter's `diff`? Either answer breaks: if core, it is not generic and will not work for a GC/N64/PS2 decomp with a different object format, reloc scheme, and diff tool (most projects use `objdiff` the binary, not a custom hexdiff); if the adapter, then `byte-match` is a 5-line wrapper and shouldn't be advertised as a core verifier with "ELF parse + reloc handling."
**Why it matters.** This is the central acceptance primitive. The seam confusion will be felt by every adapter author and will force core to grow game-specific code, violating §3.1 ("Core has zero knowledge of MWCC, PPC…").
**Fix.** Move `byte-match` out of core. Core provides a `Verifier` interface and a `compose` helper; the *adapter* ships `buildUnit`/`diff` and a `byteMatch` verifier that uses them. Rename the core "built-in" to `diff-verifier` (a thin driver that calls `adapter.diff` and interprets `DiffResult`). State explicitly that the Xenoblade adapter ports `hexdiff.py`+`reloc_map.py` as adapter code, not core. §4, §9.

### C2 — Selector→SQL compilation contradicts the "no JSON operators" portability rule. (§8 vs §3, §6.1)
**Problem.** §8: "Selectors compile to `SELECT … FROM work_items WHERE … ORDER BY … LIMIT …`" and `Selector.filter.meta` supports `eq|neq|in|contains|regex` on arbitrary meta keys. §3/§6.1 forbid `JSON1`/`JSONB` operators in queries. `meta` is a single `TEXT` JSON column. You cannot push `meta.symbol regex "…"` or `meta.region eq "us"` into a portable `WHERE` clause without JSON operators. So either (a) meta filters are post-filtered in TS after a full table scan — contradicting the "compiles to SQL" claim and killing performance on a large registry — or (b) the portability rule is violated.
**Why it matters.** `symbol`, `region`, `address`, `unit` are first-class queryable fields in v1 (`targets show`, `targets status --unit`, region filtering). Burying them in unqueryable `meta` is a regression *and* a correctness contradiction in the spec.
**Fix.** Promote the queryable core (`symbol`, `region`, `address`, `milestone`, `required_level`, `equivalence_confidence`, `equivalence_policy`) to real columns or a typed `work_item_attrs(key, value, val_type)` index table with portable equality/IN queries. Keep `meta` for genuinely unindexed blobs. Rewrite §8's compile claim to be honest about what indexes vs. post-filters. Drop the blanket "no JSON operators" rule or scope it to "core schema queries only."

### C3 — No equivalence-certificate model; migration throws away all semantic-equivalence provenance. (§6.2, §9, §19 M5)
**Problem.** v1 has a full `equivalence_certificate` system (`targets.schema.json`): `SEMANTIC_CERTIFIED` status, sha256 of retail/candidate, callee certificates chained by `certificate_sha256`, helpers, summary reads/writes — stored in a gzipped JSONL sidecar (`targets.certs.jsonl.gz`, 7MB) and loaded via `_load_certs_sidecar`. `renaming_witness.py` is a symbolic-execution + Z3 SMT equivalence prover, not a "register-renaming native tool." The spec replaces all of this with `verify: witness` (a shell-out) and `work_items.meta`. There is **no certificate table, no certificate chain, no semantic-equivalence status, no confidence tier (A/B/C), no equivalence_policy.** M5 says "migration (targets.json/ledger → SQLite)" but the ledger has nowhere to go.
**Why it matters.** Certificates are the durable, cryptographically-chained proof of equivalence and the basis for `recertify --bottom-up` (re-validate dependents when a callee changes). Dropping them is not "porting lessons," it is deleting the project's core correctness artifact. The "witness" is also mischaracterized — it is a Z3-backed symbolic prover, not a command you can shell out to trivially.
**Fix.** Add a `certificates` table: `work_item_id, status (SEMANTIC_CERTIFIED|…), evidence, retail_sha256, candidate_sha256, certificate_sha256, callees (JSON), helpers (JSON), summary (JSON), created_at`. Add `equivalence_confidence`, `equivalence_policy` columns on `work_items`. Define `witness` as an adapter-owned verifier that *emits* a certificate; the acceptance pipeline stores it. Update §9, §6.2, §13 (member/extc feed the witness), and M5 acceptance to require certificate migration with chain integrity verified.

### C4 — `member_check.py` and `extc.py` are not C++ parsing; §13 hides a missing asm/obj parser. (§13.1, §4, §19 M1)
**Problem.** §13 is titled "C++ parser & linter (tree-sitter-cpp)" and the repo layout puts all rules under `parse/cpp/rules/`. But:
- `member_check.py` parses dtk `.s` retail asm (`.fn`/`.endfn`, `/* addr hex */ insn`), builds a call graph, does r3-provenance analysis, scans `.o` files for 4-byte big-endian data pointers (`build_data_hits`), reads `config/<region>/symbols.txt`, and parses mangled `__Q…` qualifiers. None of this is C++ or tree-sitter-cpp.
- `extc.py` extracts extern "C" decls across multi-line continuations, then classifies against the retail symbol table and symbols.txt mangled names.

§13.1 lists `member.N1/N2/N3/P1/tier_b/tier_c` and `extc.*` under the C++ rule registry with a parenthetical "Retail-asm analysis, not C++ parsing" — but there is no module, interface, or milestone that owns asm/obj/symbol parsing. `parse/cpp/` cannot host them.
**Why it matters.** These are large, high-value components (member-vs-free classification is the project's hardest correctness call). The spec silently drops the infrastructure they need and then claims V1 parity. M1's acceptance names only `lint.py + smell_scan.py + detect_pointer_arithmetic.py` — quietly excluding the very files §13.1 claims parity with.
**Fix.** Split §13 into "C++ CST rules (tree-sitter-cpp)" and "Binary/asm analysis rules." Add `parse/asm/` (dtk `.s` parser, call-graph indexer, r3-provenance, `.o` data-pointer scan) and `parse/symbols/` (symbols.txt loader, mangled-name parser) to §4. Move `member.*` and `extc.*` there. Add a milestone (or fold into M2) for asm/obj parity with `member_check.py` + `extc.py`, with explicit acceptance. Stop claiming M1 delivers them.

### C5 — Delta-lint over tree-sitter-cpp is the wrong tool; the design is unstated and likely infeasible as described. (§13, §13.1)
**Problem.** `lint.py` operates on the *added-lines delta* (`difflib` opcodes), not whole files. It is deliberately line/regex oriented with cross-line state (`cast_pending` for multi-line init-list side-effects, comment stripping, `is_c` vs `is_cpp` branching). §13 declares "no regex scanning" and that tree-sitter-cpp replaces this. But tree-sitter parses *whole files*; it cannot "parse the added lines in isolation" — a CST node for an added line depends on surrounding context. Mapping a difflib delta to CST nodes (which nodes are "added"?) is a real research problem the spec doesn't address. The whole-file `smell_scan.py` genuinely benefits from a CST; the delta gate does not.
**Why it matters.** M1 is "highest-risk, highest-value" and "intentionally first." Betting it on a CST-for-delta approach that the spec doesn't actually design is a likely M1 blocker.
**Fix.** Keep the delta-lint gate as a line-oriented engine (regex + state machine), explicitly, in §13 — it is the correct design for added-lines gates. Use tree-sitter-cpp only for whole-file analyses (`smell_scan`, `clone`, `vtable`, `member.candidate` source-side). Rewrite §13's "no regex scanning" absolute into "whole-file rules use the CST; the delta gate stays line-oriented because it must operate on added lines, not parseable units."

## HIGH

### H1 — Standalone CLI mode contradicts the single-writer model and breaks claim safety. (§5, §6.3)
**Problem.** §5: "One daemon per checkout owns the store as the single writer… A CLI command is a thin RPC to the daemon **(or a standalone single-run mode for scripted/CI use, which opens the same store directly)**." If a standalone CLI opens the SQLite store directly while a daemon is running, there are two writers. SQLite WAL serializes writes at the engine level, but the spec's CAS-claim and orphan-recovery semantics (§6.3: "the daemon serializes them as the single writer") are app-level and assume one writer. A standalone CLI that claims a work item bypasses the daemon's claim serialization and orphan recovery.
**Why it matters.** This is exactly the class of bug the spec claims to fix (v1's stale-claim-in-targets.json). Reintroducing a second writer silently in CI is a concurrency hole.
**Fix.** Either (a) make the daemon mandatory and have CI start one (`decompi serve --detached` or a socket-activated daemon), with the CLI always an RPC client; or (b) specify a single-writer *lock* (flock on a sidecar file, or SQLite's own write lock) that both daemon and standalone acquire for every claim/transaction, and define orphan recovery to run on *any* process start, not just daemon start. Pick one and write it into §5/§6.3.

### H2 — Claim CAS primitive, lifecycle, and run-tie are unspecified; orphan recovery is daemon-start-only. (§6.2, §6.3, §11)
**Problem.** The `claims` schema has `work_item_id PK, owner, run_id, allowed_paths, claimed_at`. §6.3 says "CAS claim/release + orphan recovery" but: (a) no version/epoch column — a CAS claim is `UPDATE claims SET owner=? WHERE work_item_id=? AND owner IS NULL` (or `INSERT … ON CONFLICT`); the actual SQL and its portability (SQLite `ON CONFLICT` vs Postgres `ON CONFLICT` are compatible, but the spec doesn't say it); (b) no `expires_at`/heartbeat — v1 uses PID liveness; the spec says "owner PID is dead is released at daemon start" only, so a daemon that runs for days never reaps agents that die after start; (c) no FK from `claims.run_id` to `runs` and no rule tying claim release to run cancel/pause/fail — orphaned claims accumulate when runs die; (d) PID-reuse: v1's `findOrphanedClaims` explicitly guards against PID reuse (comment in `orchestrator.ts`); the spec's "owner PID is dead" has no start-time/epoch guard, so a reused PID marks a stale claim as live.
**Why it matters.** Claims are the concurrency-safety primitive. The spec hand-waves the one mechanism it repeatedly calls out as a lesson ported from v1.
**Fix.** Add `claims.epoch TEXT` (daemon start UUID) or `claims.pid_started_at TEXT` and have orphan recovery check both PID liveness and start-time match. Add `claims.expires_at` + a heartbeat refresh, and have the daemon reap expired claims periodically, not only at start. Add `FOREIGN KEY(run_id) REFERENCES runs(id) ON DELETE SET NULL` and an index on `run_id`. Specify the exact CAS SQL (`INSERT INTO claims… ON CONFLICT(work_item_id) DO NOTHING` + check `changes`), and define release-on-run-terminal behavior in §11.

### H3 — Durable assignment is "git-exported JSON," but certificates, callgraph, and dependency edges have no queryable home. (§6.3, §6.2)
**Problem.** §6.3: durable assignment lives in `work_items` and is git-exported as a canonical JSON snapshot. But v1's durable data includes a call graph (`direct_calls`, `unresolved_called_functions`, `abi_helper_calls`, `has_indirect_calls`), a dependency graph (`depends_on`), a capability graph (`capabilities`), `milestone`, `required_level`, `equivalence_confidence/policy`, and certificates (C3). The spec shoves all of it into `work_items.meta` JSON, which is unqueryable (C2). Operations like `targets sync-calls`, `recertify --bottom-up` (dependents-first revalidation), and capability-graph traversal require graph edges, not JSON blobs.
**Why it matters.** `recertify --bottom-up` is a core correctness workflow; without queryable `depends_on` edges it cannot be expressed. The spec lists `recertify` in AGENTS.md quick commands but provides no schema for it.
**Fix.** Add `work_item_deps(from_id, to_id, kind)` and `work_item_capabilities(work_item_id, capability)` tables, or at minimum a `work_item_attrs` typed KV table (C2). Add `milestone`, `required_level`, `equivalence_confidence`, `equivalence_policy` as columns. Define the git-export format to round-trip all of these, not just a flat work-item snapshot.

### H4 — Event/span write path from N×M concurrent agents to the single writer is unspecified. (§5, §11, §18)
**Problem.** Agents are pi SDK sessions (subprocesses or in-process?). Every significant action emits an event; spans wrap timed sections. The daemon is the single SQLite writer. So agents must RPC every event/span to the daemon. The spec never says this, never defines the RPC, and never addresses the hot path: with N runs × M agents each emitting per-turn events, the daemon's writer is a serial bottleneck. There is no batching, queue, or backpressure design. `events.seq INTEGER PRIMARY KEY` is "app-assigned monotonic per store" — assigned by whom, under what lock? If by the daemon, fine; if by agents, broken.
**Why it matters.** This is the throughput-critical path for "full observability" and for N×M concurrency. Unspecified = likely to deadlock or drop events under load.
**Fix.** State that agents emit events via an in-process channel to the daemon (or a local socket if subprocesses), and the daemon assigns `seq` under a single transaction-batching writer. Define a bounded queue + backpressure policy (agent blocks when the queue is full; never drops). Specify `events.seq` assignment as daemon-owned. Add an index `idx_events_run_ts ON events(run_id, ts)` for timeline queries.

### H5 — Security model is "minimal bearer token" for a daemon that mutates the repo, runs arbitrary builds, and spends money. (§16)
**Problem.** The daemon's REST API creates runs (cost-incurring), mutates source via agent sessions (repo writes), runs the build system (arbitrary shell via ninja/configure), and can select any authored pipeline `.ts` file (arbitrary code on load). §16 says only "minimal bearer token on any mutating/cost-incurring endpoint." No TLS, no default bind address, no API rate limiting, no per-action authz, no audit log of who started what run, no spend cap per token, no way to revoke. A leaked bearer = full repo compromise + unbounded spend. The agent guardrails are explicitly "not a sandbox" (§1, §11).
**Why it matters.** This is a network-exposed control plane for a money-spending, repo-mutating, shell-executing system. "Minimal" is underspecified for the threat model.
**Fix.** §16 must specify: default bind `127.0.0.1` (opt-in `0.0.0.0`), TLS termination or reverse-proxy assumption, bearer tokens with per-token spend caps and pipeline allowlists, an `audit_events` table (who/when/which run/cost), a global daemon spend cap that hard-stops new runs, and an explicit statement that exposing the daemon beyond localhost is unsupported without a fronting proxy. Add an `audit_log` table to §6.2.

### H6 — M1 acceptance excludes the files §13.1 claims parity with; milestone scoping is internally inconsistent. (§19 M1 vs §13.1)
**Problem. §13.1** header: "Rule registry (V1 parity)" and lists `member.*` (member_check.py) and `extc.*` (extc.py). M1 acceptance: "parity with `lint.py` + `smell_scan.py` + `detect_pointer_arithmetic.py` on Xenoblade sources." The omission of `detect_smells.py`, `member_check.py`, `extc.py` is silent. But `detect_smells.py` is C++-scan + targets.json cross-reference; `member_check.py`/`extc.py` are asm/obj/symbol analysis (C4). M1 cannot deliver the latter two, so the §13.1 claim is unmet by M1 and no later milestone owns them.
**Why it matters.** The milestone table is the contract; the spec's own parity claim is untestable against M1.
**Fix.** Split M1 into M1a (C++ CST rules: `lint.py`, `smell_scan.py`, `detect_pointer_arithmetic.py`, `detect_smells.py`'s source-scan portion) and M1b (asm/obj/symbol analysis: `member_check.py`, `extc.py`, witness/certificate emission). Move M1b after the store milestone (it needs symbols.txt + work-item status). Update §13.1 to label which rules land in M1a vs M1b.

### H7 — M0 acceptance requires an adapter that doesn't exist until M5. (§19 M0, M5)
**Problem.** M0 acceptance: "`select`/`status` work against an imported registry." `importWorkItems()` is a `GameAdapter` method (§7); the Xenoblade adapter is M5. No stub adapter is mentioned. So M0 has nothing to import.
**Why it matters.** M0 is unshippable as written; or it secretly depends on a stub that isn't in the milestone plan.
**Fix.** Add "stub/test adapter" to M0 deliverables (imports a JSON/CSV fixture), or move a minimal Xenoblade `importWorkItems` (targets.json → WorkItems) into M0 and reserve the full adapter (build/diff/witness/lint rules) for M5.

### H8 — `fakematch-detect` is a pipeline in v1 but a `Verifier` in the spec; semantics change. (§9, §10, §13)
**Problem.** v1's fakematch detection is a *pipeline* that runs rule families + a natural-rewrite hexdiff test to *flag candidates*. The spec promotes `fakematch` to a core `Verifier` returning a `Verdict{accepted, status, feedback}` (§9) and *also* lists a `fakematch-detect` pipeline (§10) that uses `verify: fakematch-detect`. A verifier that "rejects matches that reproduce retail codegen" turns a heuristic flag into an acceptance gate — false positives now *reject* accepted work items.
**Why it matters.** Fakematch detection is a heuristic, not a proof. Making it a reject-verifier risks blocking correct matches; the v1 design (flag → human/agent review) is deliberate.
**Fix.** Keep `fakematch-detect` as a *pipeline* that emits candidate flags as events/artifacts, not a `Verifier` that returns `accepted:false`. If a verifier form is needed, it should return a *soft* verdict (e.g., `Verdict.severity` or `Verdict.flags`) consumed by a gate step, not a hard reject. Rewrite §9 and §10 accordingly.

## MEDIUM

### M1 — `work_items.status` column conflates adapter status vocab and the canonical lifecycle. (§6.2, §8)
**Problem.** §8 says the canonical lifecycle (`pending→claimed→active→verified→accepted|rejected`) is "tracked independently of the adapter's status vocab." The schema has one `status` column. `StatusVocab` (§7) gives `accepted/rejected/pending` lists in adapter terms (e.g., `FULL_MATCH`, `EQUIVALENT_MATCH`). So either the single column holds adapter vocab (then the canonical lifecycle isn't tracked) or it holds canonical lifecycle (then adapter vocab is lost). v1 has *both* `workflow_status` (BACKLOG/DISCOVERY/QUEUED/CLAIMED/ACTIVE/ACCEPTED/REVALIDATION_REQUIRED/BLOCKED/NOT_REQUIRED) and `status` (NOT_STARTED…BEHAVIOR_VERIFIED).
**Fix.** Add two columns: `lifecycle` (canonical, core-owned) and `status` (adapter vocab). Or make `lifecycle` derived from events. Add `REVALIDATION_REQUIRED` and `BLOCKED` to the canonical vocab — v1 needs them for recertify and stuck targets; the spec's `accepted|rejected` terminal set drops them.

### M2 — No region column/index; multi-region work items in one DB. (§6.2, §7)
**Problem.** Xenoblade has us/eu/jp regions; v1 targets carry `region` per item. The build lock path is per-region. The spec's `work_items` has no `region` column (buried in `meta`), and `Selector` has no region filter. A single DB holding three regions can't efficiently select "us-region CODE_MATCH by size."
**Fix.** Add `region TEXT` column + index to `work_items` and `units`; add `region` to `Selector.filter`; thread region into `buildLockPath`/`AdapterCtx`.

### M3 — `run_workers` lacks step/progress state; resume of a multi-step pipeline is undefined. (§6.2, §11)
**Problem.** §11 lists "resume" as ported. `run_workers` has `(run_id, seq, work_item_id, status, model, started_at, finished_at)` — no step index, no per-worker progress. A paused multi-step pipeline (select → agent → verify → agent → verify) cannot resume mid-flight without knowing which step each worker is in.
**Fix.** Add `run_workers.step_index INTEGER` and `run_workers.step_state TEXT` (JSON checkpoint), or persist a `run_progress(run_id, worker_seq, step_index, state)` table. Define resume semantics in §11.

### M4 — No schema for banked near-miss drafts, rate-limit/watchdog state, or proposals. (§6.2, §11, §17)
**Problem.** §11 ports banking ("near-miss draft bank keyed by divergence, `bankOnlyOnBetter`"), rate limiting, watchdog. §17 persists "non-mutating proposals." None have schema tables. Banked drafts are artifacts? Then they need a `kind="banked-draft"` with divergence attrs and a query path (`banking.ts` needs to find "is there a better draft for this item"). Proposals have no table. Rate-limit/watchdog state is in-process and lost on daemon restart.
**Fix.** Add `drafts(work_item_id, run_id, divergence, path, created_at)` for the bank (or define `artifacts.kind="draft"` with `meta.divergence` + an index). Add `proposals(id, run_id, text, author, status, created_at)`. State that rate-limit/watchdog are best-effort in-process and reset on daemon restart (acceptable, but say it).

### M5 — Lock ordering between build lock and SQLite write lock is unspecified (deadlock risk). (§5, §11)
**Problem.** The daemon takes the repo-wide flock for builds and the SQLite write transaction for claims/events. If any path holds the SQLite write transaction while waiting for the flock, and another path holds the flock while waiting for the SQLite writer (via RPC), you have a classic AB-BA deadlock.
**Fix.** Define a lock ordering in §5/§11: always acquire build flock *outside* SQLite transactions; release the SQLite write transaction before taking the flock; agents RPC the daemon for claim/release, never hold claims while waiting on the flock. Write it down.

### H/M — `events.seq` "app-assigned monotonic per store" generator unspecified and not portable. (§6.1, §6.2)
**Problem.** §6.1 forbids `AUTOINCREMENT`/`SERIAL`, so `events.seq INTEGER PRIMARY KEY` must be app-assigned. Under the single-writer daemon `SELECT MAX(seq)+1` works, but the spec never says that, and it's not safe if standalone mode (H1) ever writes events. No generator table, no `seq_counter`.
**Fix.** Add a `counters(name TEXT PK, next INTEGER)` table (portable) or specify `SELECT COALESCE(MAX(seq),0)+1 FROM events` *inside* the daemon's write transaction. State that `seq` assignment is daemon-owned and standalone mode must RPC events.

### M6 — Adapter discovery mechanism is unspecified. (§4, §7, §15)
**Problem.** §15: "repo root auto-detected via the adapter, not a hardcoded `tools/coop/targets.json`." But how does decompi *find* the adapter for a checkout? `adapters/xenoblade/` convention? A `decompi.adapter` field in `package.json`? Env var? `adapter/registry.ts` is in the layout but its discovery rule is absent. A generic harness lives or dies by this.
**Fix.** Specify in §7: discovery order (e.g., `DECOMPI_ADAPTER` env → `decompi.config.json` `adapter` field → `adapters/<id>/` presence → fail). Define the adapter package shape (a default export implementing `GameAdapter`).

### M7 — "Clang not in scope — ever" over-absolute for a game-agnostic harness. (§13)
**Problem.** The clang-exclusion argument is sound *for Xenoblade* (MWCC extensions). But §1's goal is "generic across games." A GC decomp using a modern toolchain, or a project that already ships a compile_commands.json, would benefit from clang's type resolution for `member.candidate`/`fake_array_access`. "Ever" forecloses that adapter option.
**Fix.** Soften to: "Core ships tree-sitter-cpp only. An adapter may optionally provide a clang-backed rule backend; the Xenoblade adapter does not. Clang is not a core dependency." Keep the Xenoblade rationale.

### M8 — Tree-sitter-cpp WASM + MWCC-flavored code: error-tolerance claim needs evidence. (§13)
**Problem.** §13 asserts tree-sitter-cpp (WASM, error-tolerant) handles MWCC code that clang rejects. Tree-sitter-cpp is error-tolerant but its grammar still chokes on some MWCC constructs (`asm` blocks with register lists, `DECL_SECTION`/`DECL_WEAK` macro-prefixed `asm void` declarations — visible in `smell_scan.py`'s `RE_ASM_ENTRY`). The spec asserts parseability without a spike.
**Fix.** Add an M0/M1 spike deliverable: "parse every .cpp/.hpp in `src/kyoshin`, `libs/monolib`, `libs/nw4r` with tree-sitter-cpp; report error nodes and recovery quality on asm-decl/macro-prefixed forms." Gate M1 on acceptable error rates. Acknowledge `RE_ASM_ENTRY`-style constructs need skip-handling even with a CST.

## LOW

### L1 — No retention/pruning for `events`/`spans`/`artifacts`. (§6.2, §18)
Append-only `events` with per-turn emission across N×M agents will grow fast. No retention, checkpoint, or archival policy. **Fix:** add a `--retention-days` daemon option and a `prune` CLI; define WAL checkpoint cadence.

### L2 — `prompts` table not joined to events/spans; replay can't link a transcript to its prompt. (§6.2, §12)
Spans have `attrs` JSON but no `prompt_id` field is required. **Fix:** add `spans.prompt_id` and emit it on agent-turn spans; add `idx_spans_prompt`.

### L3 — `style_guides` table duplicates content already captured via `prompts.styleGuideHash`. (§6.2, §12)
Minor redundancy; `style_guides.content` lets the UI render the guide without reading the file, which is fine, but say so. **Fix:** one line in §12 explaining the table is for UI/replay, not a second source of truth (the file is).

### L4 — `claims.allowed_paths` is JSON-in-TEXT; no enforcement path defined. (§6.2, §11)
The spec stores `allowed_paths` but §11's "tools/allowlist… scoped-write" doesn't say the agent's write tool consults `claims.allowed_paths`. v1 enforces this in session tools. **Fix:** state in §11 that the agent write-tool allowlist is intersected with the worker's current claim `allowed_paths` at call time.

### L5 — `units` has no source-root/path set; `work_items.source` is a single path but a unit maps to many files. (§6.2)
v1 units have source paths and headers. `units.meta` bag again. Minor but affects `tu-cleanup`/`tu-header-prepass`. **Fix:** add `units.source_paths TEXT` (JSON array) or a `unit_files` table.

### L6 — `decompi hexdiff` CLI duplicates `adapter.diff`; clarify which is the user-facing path. (§15, §9)
`hexdiff` is a v1 name; in a generic harness `diff` is clearer. **Fix:** rename to `decompi diff` (keep `hexdiff` as an alias the Xenoblade adapter registers).
